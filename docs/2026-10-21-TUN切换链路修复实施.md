## P1 / D4 配置被整形并写入两次

**根因**：`kprSaveNetworkState` 先把整形结果 `prepared` 落盘（`kprBaseWriteYamlObjectAtomic`），随后 `restartClash({preparedConfig})` 又调 `writeYamlObjectAtomic`——后者会**再跑一次** `kprShapeRuntimeConfig`：又一次 `kprReadOptions`、又一次 `verifyF50TunStack` 的 mips 探针、又一次 `dumpConfigYaml`，外加一次 `Core -t` 和一次原子替换。

**改动**（`:9270`）：

```js
if (preparedConfig) {
  // preparedConfig 已由 kprShapeRuntimeConfig 整形，直接落盘，避免二次整形与重复 Core -t。
  const write = await kprBaseWriteYamlObjectAtomic(CLASH_CONFIG, preparedConfig, {label:'config.yaml',backup:false});
```

**收益**：每次模式切换少一次完整整形 + 一次核心校验。顺带消除「第一次写成功、第二次写失败」的窗口（D4）。

## D1 `f50_prepare_tun_stack` 依赖未初始化的 `$tun6_root`

**根因**：`tun6_root` 只在 `f50_check_tun_stack` 里赋值。函数间靠全局变量传递，一旦调用顺序变化，`prepare` 拿到空值，`tun6_cfg` 变成 `/Proxy/config.yaml`，报 `tun_config_mismatch`——错误信息完全指不到真正原因。

**改动**：

- `f50_prepare_tun_stack` 开头自行初始化 `F50_TUN_ROOT`；
- 函数内 3 处 `$tun6_root` 全部替换为 `$F50_TUN_ROOT`（`config.yaml`、`yq`、`Clash.Core -t`）；
- `f50_check_tun_stack` 不再设置 `tun6_root`。

**修复过程中的一次回归**：第一次改动只替换了前两处，漏了 `"$tun6_root/Proxy/Clash.Core"`，导致 `tun_stack_prepare_failed`，被 `ipv6_dns.test.js` 的版本门槛用例捕获（17 个失败）。补上第三处后恢复。这说明该测试确实在守着这条链路。

**收益**：消除一类难以复现的启动失败。

## D2 八个错误码补齐文案

**根因**：`f50_check_mips_version` 返回 2、TUN 阶段失败等场景会输出裸错误码，`F50_DIAGNOSTIC_LABELS` 里没有对应键，用户只看到 `F50_ERROR=xxx`。

**改动**（`:1050` 起）新增 8 条：

```
mips_core_version_unavailable      无法读取 Mihomo 版本；请确认核心文件存在且可执行。
tun_policy_apply_failed            TUN 已启动，但网络接管规则应用失败；请执行"恢复网络"后重试。
tun_policy_verify_failed           TUN 已启动，但接管规则校验未通过；请执行"恢复网络"后重试。
tun_return_route_apply_failed      TUN 已启动，但 IPv6 回程路由写入失败；IPv6 出站可能不可用。
tun_return_route_verify_failed     TUN 已启动，但 IPv6 回程路由校验未通过；IPv6 出站可能不可用。
tun6_address_query_failed          无法读取 KanoTun 的 IPv6 地址；请确认 TUN 接口已创建且 IPv6 已开启。
tun6_address_parse_failed          KanoTun 的 IPv6 地址无法解析；请检查接口地址是否异常。
tun6_route_query_failed            无法查询 IPv6 路由表；请检查设备 ip 命令与权限。
```

同时把这 8 条登记进 `tests/gist-sync/expected-contracts.json` 的 `labels`——`cleanup.test.js` 的「诊断标签完整性」用例要求所有新增标签入册。

**收益**：失败可诊断，不再需要用户提供裸错误码才能定位。

## D3 `f50_finish_tun_stack` 失败不区分阶段

**根因**：四步用 `&&` 串联，任一步失败只 `return 1`，从输出看不出是 `policy apply` 挂了还是回程路由挂了。

**改动**：

```sh
f50_run_controller policy apply || { echo F50_ERROR=tun_policy_apply_failed; return 1; }
f50_tun6_return_route apply || { echo F50_ERROR=tun_return_route_apply_failed; return 1; }
f50_run_controller policy verify || { echo F50_ERROR=tun_policy_verify_failed; return 1; }
f50_tun6_return_route verify || { echo F50_ERROR=tun_return_route_verify_failed; return 1; }
```

**收益**：`lastInstallDiagnostic` 能直接指到失败阶段，配合 D2 的文案即可读。

## D6 回程路由查询失败无错误码

**根因**：`ip -6 route show` 失败直接 `|| return 1`，与「路由不存在」无法区分。同类的地址查询、地址解析也是裸 `return 1`。

**改动**：三处 `return 1` 改为带码输出（`tun6_address_query_failed` / `tun6_address_parse_failed` / `tun6_route_query_failed`）。

**收益**：区分「命令失败」与「结果不符合预期」。

## P3 options.conf 被反复读取

**根因**：`check` 读 3 次（`traffic_mode`、`tun_stack`、`ipv6`），`prepare`、`finish`、`tun6_return_route` 各自再读。一次启动 6~7 个 `grep`/`sed` 进程。

**改动**：新增 `f50_load_tun_state()`，用一次 awk + 一次 while 循环读进 `F50_TUN_MODE` / `F50_TUN_IPV6` / `F50_TUN_STACK`；`check` 调用它，`prepare` / `tun6_return_route` 在变量为空时按需调用。

```sh
f50_load_tun_state() {
  F50_TUN_ROOT=${CLASH_ROOT:-${F50_ROOT:-/data/clash}}
  F50_TUN_FILE="$F50_TUN_ROOT/Policy/options.conf"
  F50_TUN_MODE=''; F50_TUN_IPV6=''; F50_TUN_STACK=''
  [ -r "$F50_TUN_FILE" ] || return 1
  f50_tun_lines=$(awk '/^(traffic_mode|ipv6|tun_stack)=/' "$F50_TUN_FILE" 2>/dev/null)
  while IFS='=' read -r f50_tun_key f50_tun_value; do
    case "$f50_tun_key" in
      traffic_mode) F50_TUN_MODE=$f50_tun_value;;
      ipv6) F50_TUN_IPV6=$f50_tun_value;;
      tun_stack) F50_TUN_STACK=$f50_tun_value;;
    esac
  done <<F50_TUN_STATE
$f50_tun_lines
F50_TUN_STATE
  return 0
}
```

**注意**：用 heredoc 而不是管道喂 while。管道会让循环在子 shell 里跑，变量出了循环就丢。

**收益**：一次启动的读取进程从 6~7 个降到 1~2 个。

## R2 / M3 / D5 `networkStateKey` 整理

**根因**：`runtimeOnly` 布尔参数（为 `true` 时比较的键反而更少，语义反直觉）；键表硬编码在函数体里，新增字段容易漏；`transparent` 会被 `kprSaveNetworkState` 改写却不在键表内。

**改动**：

```js
const NETWORK_RUNTIME_FIELDS = ['traffic_mode', 'transparent', 'ipv6', 'tun_stack', 'dns_hijack', 'dns_port', 'private_route_enabled', 'private_route_cidrs', 'private_route_policy', 'tproxy_port'];
const NETWORK_EXTRA_FIELDS = ['quic_block', 'proxy_group'];
const NETWORK_LIST_FIELDS = ['deviceBypass', 'directDomain', 'directIp', 'proxyDomain', 'rejectDomain'];

function networkStateKey(state, { runtimeOnly = false } = {}) { ... }
```

调用点同步改为 `networkStateKey(previous, { runtimeOnly: true })`。

**收益**：键表集中，新增 options 字段时有明确的登记位置；`transparent` 不再是隐形依赖。

**风险**：历史数据里 `transparent` 可能与 `traffic_mode` 不一致，会触发一次额外重建，之后稳定。

## M4 补 Service 侧 TUN 函数测试

**根因**：`f50_check_tun_stack` / `prepare` / `finish` 之前只有 `sh -n` 语法检查，分支逻辑零覆盖。

**新增** `tests/tproxy/tun_stack.test.js`，9 个用例：

| 用例 | 覆盖点 |
|---|---|
| auto + 新版内核 → mips | 正常选栈 |
| auto + IPv4 旧内核 → mixed | 回退与 `F50_TUN_AUTO_FALLBACK` |
| auto + IPv6 旧内核 → gvisor | 双栈回退 |
| 显式 mixed 不探版本 | 短路条件 |
| 显式 mips + 旧内核 | 直接失败与错误码 |
| 非法 stack | `invalid_tun_stack` |
| 非 TUN 模式 | 不选栈 |
| prepare 单独调用 | **D1 回归**：不依赖 check 的全局变量 |
| finish 各阶段失败 | **D3 回归**：独立错误码 |

**有效性验证**：把 `tun6_cfg` 临时改回 `$tun6_root` 后，第 8 个用例失败；改回后通过。证明测试能捕获该缺陷，不是空跑。

## P2 已撤销：探针缓存引入状态泄漏

**原方案**：`verifyF50TunStack` 按 `ipv6|tun_stack` 做 60 秒缓存，省一次 `Clash.Core -v`。

**为什么撤销**：加上后 `ipv6_dns.test.js` 出现 15 个失败。根因是缓存键不包含内核版本——同一组设置下换了内核，60 秒内仍返回旧结论。测试连续用不同版本 mock 调用，第二次直接命中第一次的缓存。

这不是测试太苛刻，而是缓存本身错了：**探针结果与内核版本强相关，而内核版本不在键里**。要正确缓存就得把 `Clash.Core` 的 mtime/size 纳入键，那又要多一次 shell 调用，收益被吃掉。

代码里保留了注释说明为什么不做：

```js
// 探针结果与内核版本强相关，不做跨调用缓存：换了内核后旧结果会让 stack 判断失真。
```
