## 二、逐项修复（位置 / 代码 / 理由 / 影响）

### P1 yq 合并被手改配置打死

**位置**：`猫猫TProxy.js` → `buildF50OriginalConfigFunctions()` 内的 `f50_restore_original_config`，标记 `KANO_ORIGINAL_CONFIG_PRESERVATION`。

**根因**：上一轮为修复「模板分支未贯通启动」引入了 dns/tun/sniffer/profile 四组子键合并，但 yq 的 `*` 只接受 map。用户在设备上手改配置时完全可能写成 `sniffer: on`、`profile: [a,b]`、`dns: nope`，此时整个表达式报错 → 启动被 `original_config_merge_failed` 拦死。

**修复**（`ed8c6fd`）：在表达式开头把四个键一次性归一化，非法值直接丢键（由控制器生成的值兜底），合法的用户 map 照旧合并：

```yaml
. as $runtime | load(strenv(F50_ORIGINAL_CONFIG)) as $original |
($original."x-f50-gist-sync" == true and strenv(F50_CONFIG_SOURCE) == "uploaded_config") as $gist |
($original | with_entries(select((.value | tag) == "!!map" or (.key | test("^(dns|tun|sniffer|profile)$") | not)))) as $original |
```

同时 `KANO_ORIGINAL_CONFIG_PRESERVATION` 18 → 19（三处同步：函数头、`grep -qx` 判断、awk skip 正则），否则设备上的旧 Service 不会被升级。

**理由**：用 `with_entries` 一次归一，而不是给四个键各写一个 `// {}` 兜底——`select(cond) | {}` 在条件为假时**仍然产出一个空文档**（空流右侧照样执行一次），会让合并输出两份 YAML，报 `yaml: duplicate mapping key`。只有 `//` 会吃掉空流，而四个键各写一次太占体积（安装脚本预算见下）。

**影响**：仅改变「用户把受控键写成非法类型」时的行为——从启动失败变为忽略该键、用生成值兜底。合法配置的行为完全不变。

**体积**：`optimization_network` 要求安装脚本比旧基线小 25000 字节，当时 saving=25015，只剩 15 字节。因此解释性注释全部移到 JS 侧（`function buildF50OriginalConfigFunctions()` 上方），生成的 shell 里一行都不多（中文注释 1 字符=3 字节）。改完脚本反而比 HEAD 小 122 字节。

### P2 只比类型、不比地址（假更新主因）

**位置**：`updateSubProviders`，`cleanConvertMode === SUB_CONVERT_MODE_PROVIDER` 分支。

**根因**：`modeReady` 只检查 `definitions[name].type === expectedType`，地址变化不会触发重建，于是 `forceUpdateProvidersFromConfig` 按配置里的**旧 URL** 重新下载一次，mihomo 返回 200 → 插件报成功。用户看到「成功」但节点当然没变。

**修复**（`e2b0c63`）：与类型不一致同等处理——地址不一致时先按当前订阅设置重建配置再更新：

```js
const addressDrift = cleanSources.filter((source) => {
  const def = definitions[source.name];
  return def && def.type === 'http' && String(def.url || '') !== source.url;
});
if (addressDrift.length) {
  createToast('订阅地址已变化；正在按新地址重建配置…', 'yellow', 6000);
  return saveSubSources(await readCurrentSubSources({ includeDisabled: true }), cleanMode, cleanConvertMode, { applyToCustom: true });
}
```

**理由**：地址漂移和类型漂移是同一类问题（运行配置与订阅设置不一致），复用已有的重建路径最稳，不新增一条独立的配置写入逻辑。

**影响**：改链接后点更新，会先重建配置（黄色提示），再真实下载新地址。地址没变时行为完全不变，不会多做一次重建。

### P3 自定义配置静默按旧地址更新

**位置**：`updateSubProviders` 的 `uploaded_config` 分支。

**修复**：检测到地址漂移时明确提示，并说明如何生效：

```js
const addressDrift = normalizeSubSourceList(storedSources).filter((source) => {
  const def = definitions[source.name];
  return def && def.type === 'http' && String(def.url || '') !== source.url;
});
if (addressDrift.length) {
  createToast(`订阅设置中的地址与当前自定义配置不一致（${safeTextToHtml(addressDrift.map((s) => s.name).join('、'))}）；本次仍按配置内的地址更新。<br>如需改用新地址，请在订阅设置中勾选“应用到自定义配置”后重新保存。`, 'yellow', 12000);
}
```

**理由**：自定义配置的语义就是「以配置为准」，不能擅自改写用户文件；但也不能默默按旧地址更新完还给绿色成功提示——那正是用户描述的「假更新」。

**影响**：只增加一条黄色提示，不改变下载行为。

### P4 让「成功」可被验证

**位置**：`forceUpdateProvidersFromConfig`。

**修复**：PUT 前先 GET 一次快照，结果里带 `previousProxyCount` 与 `unchanged`，结果对话框显示 `更新前 N 个 → 当前 M 个（节点内容与更新前一致）`。

```js
const before = await callMihomoApi(path, 'GET', null, info, 5, { corePid: pid });
let previousCount = null;
if (before.success) {
  try { const value = JSON.parse(before.responseText || ''); if (Array.isArray(value.proxies)) previousCount = value.proxies.length; } catch (_) {}
}
const updated = await callMihomoApi(path, 'PUT', null, info, 5, { corePid: pid });
```

**理由**：订阅内容本身没变时（服务端还是那批节点），用户看到「成功」会以为没生效。把「更新前后数量」摊开，能立刻区分「没下载」和「下载了但内容一样」。API 调用序因此变成 `[GET, PUT, GET]`，测试断言同步更新。

**影响**：每个节点来源多一次 GET（本地、开销可忽略）；`unchanged` 只是展示字段，不改变 `ok` 判定，不会把正常更新误标失败。

## 四、设备本地转换（`fetch-batch`）沙箱验证

`convertSubscriptionsLocally` 走 `f50Command('fetch-batch')` → `Scripts/clashctl_arm64` → `Tools/kano-f50-helper-converter` → `Proxy/proxies/<name>.yaml`。这条链此前只有失败分支用例，本次用 qemu + 桩件（stub curl / stub converter）把它跑了一遍。

**结论 1：每次调用都真实下载，没有缓存跳过。** 同一目录连续两次 `fetch-batch`（两个不同 URL），stub curl 被调起 2 次、URL 分别是第一次和第二次的请求地址，stub converter 也被调用 2 次。所以本地转换模式不存在「看起来成功、实际复用旧结果」的短路。

**结论 2：「Mihomo YAML」判定只接受 JSON。** YAML 文本一律落到 converter 分支；converter 不存在时报 `subscription is not Mihomo YAML and local URI converter failed`。而 converter 的**输出必须是 JSON object**——输出 YAML 文本会被判 `subscription is not a YAML/JSON object`（`proxies: []` → `subscription contains no proxy nodes`，缺 `type` → `invalid proxy node`，说明结构确实被读到了）。

**结论 3：沙箱内构造不出「成功提交」。** 任何带合法节点的 JSON 都会走到 `node validation failed: `（原因串为空），socks5 / http / ss / vmess / trojan / direct、IP 或域名 server、port 数字或字符串，全部一致。疑似该版本控制器（`8.0.0-compat.2.3`）的节点校验依赖未在精简构建中注册的解析器。因此成功路径无法在沙箱内复现，改用「下载次数」这个可观测行为来固化回归。

**回归补齐**（`tests/tproxy/http_subscription.test.js`，新增 1 例）：

```
ok 19 - ARM64 download re-fetches on every call instead of reusing the previous result
```

它连跑两次不同 URL 的 `fetch-batch`，断言 curl 日志为 `[first-subscription, second-subscription]`、converter 日志为 2 行。若将来引入任何「已存在就跳过」的缓存，这条会立刻变红。

**残留风险（真机排查建议）**：若真机本地转换模式仍报失败，优先看 `Tools/kano-f50-helper-converter` 是否存在、是否输出 JSON object，以及失败文案是否落到 `formatSubscriptionDownloadError` 的通用分支（「订阅返回内容无法识别」）——那是提示不够精确，不是下载失败。

## 五、验证步骤与测试建议

**必须跑（全量回归只能在 WSL 跑）**：Windows 侧跑 qemu 用例会撞 `spawnSync` 的 30s 超时（表现为 stdout 空、`status` 超时），且 `tar` 读 zip 需要 bsdtar shim。可用命令：

```
wsl -d Debian -- bash -c 'mkdir -p /tmp/f50-shim; ln -sf /usr/bin/bsdtar /tmp/f50-shim/tar; \
  export PATH=/tmp/f50-shim:/usr/local/bin:/usr/bin:/bin; \
  cd /mnt/c/Users/Cuty/Desktop/Github/Tproxy-F50 && \
  F50_TEST_YQ=$PWD/.cache/gist-sync/tools/yq-linux-amd64 \
  F50_TEST_QEMU=$PWD/.cache/gist-sync/tools/qemu-aarch64 node scripts/verify_plugin.js'
```

注意：`bash -c` 的单引号里不要展开 `$PATH`（Windows PATH 含 `Program Files (x86)`，括号会把 bash 语法打爆）；`$PWD` 在 WSL 内展开是 `/mnt/c/...`，正确。

**改动后按发布顺序重建交付物**（P7 的防线）：

```
python3 scripts/build_gist_sync.py
node scripts/verify_plugin.js          # 必须 failed=0
node scripts/report_plugin.js
python3 scripts/package_plugin.py
```
