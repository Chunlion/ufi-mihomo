# 「订阅与配置」「网络与诊断」二级菜单响应偏慢：原因与优化方案

分析对象：`猫猫TProxy.js`（v9.0.0，12135 行）
分析方式：静态调用链 + 命令计数（未在真机取时，结论中的耗时为区间估算，验证方法见第 5 节）

## 1. 结论先说

慢的根因不是菜单展开，也不是弹窗渲染，而是**每个二级菜单项在弹窗出现前要跑一条串行的设备 Shell 链**，而这条链上的每一跳都要付完整的租约 + 任务回执开销。

三条主因，按影响排序：

1. **首次点击的冷启动成本**（`ensureCompatBackend`，1023 行）：对 `clashctl_arm64` 做全量 `sha256sum` + 字节段校验 + 起 `Clash.Service version` 子进程。`f50BackendReady` 只是内存变量，**每次刷新页面后的第一个订阅/网络按钮必然重付一次**，这是「刚打开面板时特别慢、用一会儿就快了」的直接原因。
2. **命令粒度过细**：同一份 `subscription_urls.txt` 在「订阅设置」里被 3 条独立命令分别读（10660 / 4897 / 4930 行），`config.yaml` 还会走 `readYamlObject` 全量 `yq → JSON → 前端 JSON.parse`（5423 行，上限 8 MB）。
3. **先取数后渲染**：所有弹窗都是 `await 数据 → createFixedToast`，没有骨架屏。真实延迟 100% 暴露给用户；同组内的「配置文件」弹窗（11265 行起）恰好是唯一「先渲染、后填充」的实现，所以它不慢。

菜单本身（`appendActionGroup`，12063 行）是纯 `<details>` + CSS grid，展开无任何网络请求，不是瓶颈，不需要动。

## 2. 现状：每个入口的往返次数

「冷」= 页面加载后首次点击（`whoami` 缓存未命中 + `f50BackendReady === false`）
「热」= 30 秒内点过任意同类按钮

| 主菜单 | 二级菜单项 | 入口 | 冷路径命令数 | 热路径命令数 | 说明 |
| --- | --- | --- | --- | --- | --- |
| 订阅与配置 | 订阅设置 | 11475 | ~7 | 4~6 | 4 项并发读 + 同文件重复读 + 可能触发 yq |
| 订阅与配置 | 订阅 User-Agent | 9958 | ~4 | 2 | `loadProviderUserAgent({ fresh: true })` 强制绕过缓存 |
| 订阅与配置 | 配置文件 | 11259 | 1 | 1 | 唯一「先渲染后加载」的入口 |
| 订阅与配置 | 图形规则 | 11849 | 3 | 2~3 | `readYamlObject` 全量 yq 解析 config.yaml |
| 网络与诊断 | 网络设置 | 11921 | 3 | 2 | `readPolicyState` 一条命令读 6 个文件（正确范式） |
| 网络与诊断 | 状态与日志 | 9939 | 9~10 | 8~9 | `showStatusDiagnostic` 并发 8 项，含 2 次 Mihomo API |

命令计数依据：

- `ensureReady`（7462）= `ensureAdvanced`（`whoami`，4614）+ `ensureInstalled`（`ensureCompatBackend`，1023）
- `importSub`（11265）的 `Promise.all` 实际是 4 条独立命令，不是 1 条
- `showStatusDiagnostic`（8089）：`readStatusSnapshot` + `runtimePreflight` + `buildControllerInfo` + `readPolicyState` + `configPromise` + `processPromise` + `logPromise` + `/version` + `/connections`

## 3. 瓶颈点拆解

### P1 每条命令的固定开销远大于命令本身

`runShellWithRoot`（3809）给**每次调用**套了完整外壳：

- `buildF50LeaseFunctions()`（303 行起，约 100 行 shell）全量拼接下发
- `f50_lease_acquire` 一次独立往返（首次）
- 主命令里 `mkdir` 互斥锁自旋（0.1 s 步进，最多 20 次）、`chmod`、写 owner
- `fork sh -c` 后台子进程 + 写 task 记录 + `wait` + 写 receipt + `mv` + `sed` + `rm` + 解锁
- 结束再 `f50_lease_release` 一次往返（含收尾 `f50_task_receipt` 校验）

一条「读一行文件」的真实成本 ≈ 一次通道往返 + 一段 4~6 KB shell 的解析与十余次文件系统操作。在 UFI 这类 ARM 低端设备上，这比命令本体的 `sed`/`cat` 贵一到两个数量级。

### P2 并发不是并行

`Promise.all` 在 JS 侧同时发出，但设备侧所有命令都要过同一个 `f50_writer_enter`（mkdir 全局锁），临界区串行；若宿主的 root shell 通道本身是单连接串行，则完全退化为线性排队。所以 `showStatusDiagnostic` 的「并发 8 项」实际耗时接近 8 × 单次往返。

### P3 缓存 TTL 与真实使用间隔不匹配

| 缓存 | TTL | 位置 |
| --- | --- | --- |
| `advancedAccessCache` | 30 s | 3500 |
| `statusSnapshotCache` | 2 s | 3330 |
| `controllerInfoCache` | 1.5 s | 3499 |
| `runtimePreflightCache` | 1.5 s | 7450 |

用户两次点菜单的间隔通常是分钟级，以上缓存**命中率接近 0**。唯一长期有效的是 `f50BackendReady`（直到刷新页面），这正好解释了冷/热差异。

### P4 弹窗零骨架

`subBtn`、`policyToolsBtn`、`editBtn`、`userAgentBtn` 都是 `await` 完数据才 `createFixedToast`。`subBtn` 还会先 `runCriticalOperation` 起浮动进度条，但弹窗本体仍然要等 4~6 条命令跑完。

### P5 同一文件重复读 + 全量 YAML 解析

- `subscription_urls.txt`：`readCurrentSubSources`（10661）、`readCurrentSubRuleMode`（4898）、`readSavedSubConvertMode`（4931）各读一次
- `readSavedSubConvertMode` 在无 `# KANO_SUB_CONVERT_MODE` 头时会回落 `readYamlObject`（4940）
- `readYamlObject` 用 yq 把整份 `config.yaml` 转 JSON 传回前端再 `JSON.parse`，大配置下是秒级；「图形规则」打开路径上必付

### P6 权限校验串在数据读取之前

`ensureReady` → 数据读取 → 渲染，三段串行。`whoami` 与数据读互相独立，完全可以并行，失败再丢弃结果。

### P7 冷启动重脚本

`ensureCompatBackend`（1025）除了 patch 校验，还要对 ARM64 控制器的几十 MB 二进制做 `sha256sum`，并起 `Clash.Service version`。这是「每次开页面第一次点特别慢」的主要构成。

## 4. 优化方案与对比

### 方案 A：感知层（先渲染，后填充）

把「配置文件」弹窗（11265 行）的写法推广到其余入口。

- 点击即 `createFixedToast`，字段用 `--` / 骨架占位
- `setButtonBusy` 统一加到 `subBtn`、`policyToolsBtn`、`editBtn`、`userAgentBtn`（现在这 4 个都没即时反馈）
- 数据到达后局部 `setText`，失败在弹窗内提示，不阻塞弹窗

| 项 | 值 |
| --- | --- |
| 改动量 | ~120 行，集中在 4 个 onclick + 2 个 dialog |
| 风险 | 低（不触碰写路径、租约、事务） |
| 预期 | 弹窗出现延迟从 0.8~2.4 s 降至 <0.1 s；数据填充仍在原时长，但有可见加载态 |

### 方案 B：请求层（合并读 + 有效缓存 + 并行校验）

1. **一条聚合读替代 4~5 条**：仿 `readPolicyState`（8411，单命令读 6 文件 + 前缀标记），把订阅设置需要的 4 项合成一条：
   `KANO_SUB_RULE_MODE` / `KANO_CONFIG_SOURCE` / `KANO_SUB_CONVERT_MODE` / `subscription_urls.txt` 全文，一次返回再前端拆解。
2. **缓存 + 写后失效**：订阅/网络设置读到的是小型文本，只在保存动作后变化。TTL 提到 60 s，并在 `saveSubSources`、`savePolicyOptions` 等写成功处调用已有的 `invalidateStatusSnapshot` 同款失效钩子。
3. **权限校验并行**：`ensureReady` 与数据读 `Promise.all`，失败再丢弃。
4. **`loadProviderUserAgent` 去掉 `fresh: true`**：改为常规 TTL 缓存 + 保存后失效。

| 项 | 值 |
| --- | --- |
| 改动量 | ~200 行，新增 1 条聚合脚本 + 2 个缓存 |
| 风险 | 低~中（聚合脚本要保证标记解析健壮；缓存失效漏一处会显示旧值） |
| 预期 | 订阅设置 4~6 条 → 1~2 条；状态与日志 8~9 条 → 4~5 条（合并 `readStatusSnapshot` 与 `readPolicyState` 的重复读，`/version` 与 `/connections` 合并为一次 curl） |

### 方案 C：通道层（只读走轻量通道）

`whoami`（4614）和 `readStatusSnapshot`（3319）已经直接调 `hostRunShellWithRoot`，绕过了租约/回执。把同类**只读**命令（订阅读取、策略读取、文件读取、日志 tail）统一走这条轻通道，只在写操作进行中（`activeCriticalOperation !== null`）拒绝发起。

安全性依据：写路径已经是「候选文件 + 原子 `mv`」（`stageTextBesideTarget` / `commitStagedYaml`），读方不会看到半成品；`buildF50GistFence` 的只读检查仍保留。

| 项 | 值 |
| --- | --- |
| 改动量 | ~150 行（抽一个 `runReadShell`）+ 回归测试 |
| 风险 | 中（需逐条确认「读不参与写事务一致性」，特别是 gist 事务与 config 事务窗口） |
| 预期 | 单条读命令从「1 往返 + 完整租约壳」降到「1 往返 + 精简壳」，单次省 40~60%；配合方案 B 后弹窗数据就绪进入 0.5 s 内 |

### 方案 D：设备层（Service 提供聚合查询）

在组件包 `Clash.Service` 增加只读子命令 `status --json` / `sub-settings --json`，一次返回 UI 需要的全部字段（含 yq 解析后的精简投影，而不是整份 JSON）。

| 项 | 值 |
| --- | --- |
| 改动量 | 组件包改动 + 协议版本 + 兼容分支，1~2 周 |
| 风险 | 高（要跟组件包版本、升级路径、卸载/回滚一起发布） |
| 预期 | 任何弹窗 ≤1 往返，0.3~0.6 s；同时消除 8 MB YAML 回传 |

### 对比

| 方案 | 往返数下降 | 感知延迟 | 风险 | 工作量 | 建议 |
| --- | --- | --- | --- | --- | --- |
| A 感知层 | 0 | **最大**（弹窗即时） | 低 | 小 | P0，先做 |
| B 请求层 | 50~70% | 中 | 低~中 | 中 | P1，与 A 同期 |
| C 通道层 | 每条再省 40~60% | 中 | 中 | 中 | P2，A+B 之后按实测决定 |
| D 设备层 | 到 1 条 | 最大 | 高 | 大 | P3，前三个仍不达标才做 |

## 5. 落地顺序与验证

**P0（当天可完成）**

1. 4 个按钮补 `setButtonBusy`
2. 订阅设置、网络设置改成先渲染后填充
3. `ensureCompatBackend` 预热：在 `collapse_mm` 展开回调（12102）里后台跑一次，用户点按钮时已就绪

**P1（1~2 天）**

4. 订阅设置单条聚合读
5. 订阅/网络设置缓存 60 s + 写后失效
6. `whoami` 与数据读并行

**P2（按实测决定）**

7. 只读命令走轻通道
8. `/version` + `/connections` 合并为一次 curl

**测量方法（先做，否则无法判断收益归属）**

在 `runShellWithRoot`（3809）入口与返回处各打一个 `performance.now()`，把 `label`、耗时、命令字节数写入现有的 `appendTemplateFlowDebug`（3977）环形缓冲。跑一轮后即可区分：

- 若单条命令耗时稳定在 300 ms 以上且与命令体大小弱相关 → 主因是通道往返，方案 B/C 收益最大
- 若耗时随命令字节数明显上升 → 主因是 lease 壳，方案 C 收益最大
- 若首次点击与后续点击差 1 s 以上 → 主因是 `ensureCompatBackend`，P0 第 3 项即可解决大半

**验收标准**

- 冷启动（刷新页面后首次点击）：订阅设置弹窗 ≤0.3 s 出现
- 热路径：订阅设置数据就绪 ≤0.8 s，网络设置 ≤0.4 s，状态与日志 ≤1.5 s
- 对比基准须来自同一设备、同一 WiFi、同一测量脚本

## 6. 不建议做的事

- 不给 `<details>` 加懒加载或按钮防抖：菜单展开本来就无请求，防抖只会让用户觉得按钮失灵
- 不为了快就缩短或去掉租约校验、`f50_writer_enter`、receipt 校验：这是写事务一致性的唯一保障
- 不无限加长 TTL 而不做写后失效：会读到旧配置并在保存时用旧 revision 覆盖新状态，比慢更糟
- 不把 `readYamlObject` 的上限调小来「提速」：那是保护，不是性能开关
