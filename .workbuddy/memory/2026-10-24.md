## 最终根因：两套 fake-ip 池冲突（非节点问题）

用户用 SNAT 把本机流量送到 F50，F50 看到的 sourceIP 是 `192.168.0.248`。F50 日志确有记录：

```
[TCP] 192.168.0.248:57289 --> github.com:443 match Match using 兜底流量[🇭🇰HKG ⭐ Ciallo 01]
```

对照实验定位：

```
F50 DNS (192.168.0.1:1053)  github.com = 198.18.0.83
本机系统 DNS                github.com = 198.18.0.78   ← Sparkle 的池
F50 DNS  api.github.com = 198.18.0.52
本机 DNS api.github.com = 198.18.0.52   ← 恰好相同，所以能通
```

`sparkle-service` 仍在运行并接管本机 DNS，Sparkle 的 fake-ip 池与 F50 的池是两个独立映射。本机连 `198.18.0.78` 经 SNAT 到 F50，F50 池里该 IP 对应别的域名 → 还原错乱 → TLS 握手失败。`api.github.com` 两边恰好同 IP 所以正常，造成「只有 github.com 坏」的假象。

修复：彻底停 `sparkle-service` + `ipconfig /flushdns`，让 DNS 只由 F50 提供（或直接用 F50 的 1053）。之前「节点 REALITY 认证失败」是 Sparkle 日志里的另一条问题线，不是本次主因。

## 劫持覆盖面核查（10-25 10:32）

设备 `ip link show up`：`lo dummy0 sipa_dummy0 sipa_eth0 usb0 usb1 br0 tailscale0`。而：

```
mangle PREROUTING : -A PREROUTING -i br0 -j KANO_F50_PRE
nat    PREROUTING : -A PREROUTING -i br0 -p tcp/udp --dport 53 -j KANO_F50_DNS
```

只有 br0 被覆盖。关键事实：**dnsmasq 根本没有上游**——`/proc/2300/cmdline` 是
`--keep-in-foreground --no-resolv --no-poll --dhcp-authoritative --dhcp-option-force=43,ANDROID_METERED --pid-file --listen-mark 0xf0063 --user dns_tether --address=/ufi.ztedevice.com/192.168.0.1`，**没有任何 `--server=`**。

也就是说：任何绕过劫持的 DNS 查询（连 usb0/usb1/tailscale0，或 `device_bypass.txt` 里 ACCEPT 掉的设备）到达 192.168.0.1:53 时，除了 `ufi.ztedevice.com` 一律没有答案。劫持覆盖是「有 DNS」的唯一前提，不是可选项。

所以 Chrome 的 `ERR_CERT_COMMON_NAME_INVALID` 不是劫持缺口造成的（那会是 SERVFAIL/无 DNS），而是 fake-ip 地址被回收后重新分配给别的域名，客户端仍拿旧 IP 去连 → 返回别人的证书。
