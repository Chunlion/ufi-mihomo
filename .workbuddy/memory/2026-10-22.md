# 2026-10-22

## 设备本地转换链路（fetch-batch）沙箱验证 + 回归补齐

补完了 10-21 遗留的「fetch-batch 是否每次真下载」。方法：qemu 跑打过补丁的 `clashctl_arm64`，用 stub curl / stub converter 观察行为（调试脚本在 `.cache/dbg_fetch8~16.js`）。

**结论（重要）**：
1. **每次调用都真实下载**：同一目录连跑两次（不同 URL），curl 被调 2 次、URL 分别是两次的请求地址，converter 也被调 2 次 → 本地转换模式没有「复用旧结果」的短路，「假更新」不在这层。
2. **「Mihomo YAML」判定只接受 JSON**：YAML 文本一律落到 converter 分支；converter 不存在时报 `subscription is not Mihomo YAML and local URI converter failed`。converter 的**输出也必须是 JSON object**，输出 YAML 会被判 `subscription is not a YAML/JSON object`（`proxies: []` → `contains no proxy nodes`；缺 `type` → `invalid proxy node`，说明结构读到了）。
3. **沙箱构造不出成功提交**：任何合法节点（socks5/http/ss/vmess/trojan/direct、IP 或域名、port 数字或字符串）都停在 `node validation failed: `（原因串为空）。疑似 8.0.0-compat.2.3 的节点校验依赖未注册的解析器。故改用「下载次数」这一可观测行为固化回归，而不是断言 ok:true。

**回归**：`http_subscription.test.js` 新增 `ARM64 download re-fetches on every call instead of reusing the previous result`（跑两次不同 URL，断言 curl 日志 = 两个 URL、converter 日志 2 行）。将来任何「已存在就跳过」的缓存都会让它变红。全量 **644 passed / 0 failed**。

## 环境坑（Windows 侧跑 qemu 用例不可行）

- 测试里 `native()` 的 `spawnSync(..., timeout: 30000)` 在 Windows 侧会超时（stdout 空、31.5s）。**qemu 用例必须在 WSL 内跑**（node 走 linux 分支，不再套一层 `wsl`）。
- WSL 命令里 `F50_TEST_QEMU` 用 `$PWD/...` 没问题（WSL 内 PWD 是 `/mnt/c/...`）；但**在 Windows 侧跑 node 时必须传 Windows 风格路径**（`C:/Users/...`）——Git Bash 环境变量里的 `/c/Users/...` 经 `linuxPath()` 会变成 `/mnt//Users/...`。
- `/tmp/f50-bintar` 每次会被清：`mkdir -p /tmp/f50-bintar && cp /c/Windows/System32/tar.exe /tmp/f50-bintar/tar.exe`（Windows 自带的就是 bsdtar），再前置 PATH；不要前置整个 System32。WSL 侧则是 `ln -sf /usr/bin/bsdtar /tmp/f50-shim/tar`。
