# TUN 切换链路优化方案

范围：从「网络设置」保存到 TUN 生效的完整链路
`kprSaveNetworkState`(:3092) → `kprShapeRuntimeConfig`(:2997) → `KPR.runtime`(:2876) → `restartClash`(:9266) → Service `f50_check_tun_stack`(:1639) / `f50_prepare_tun_stack`(:1659) / `f50_finish_tun_stack`(:1679)

本文只给方案，不改代码：这条链路是启动热路径，改错会让设备起不来，需先有实机验证条件。

---

## 一、性能

### P1 同一份配置被整形并写入两次（收益最大）

**现象**：`kprSaveNetworkState` 先在 :3138 调 `kprBaseWriteYamlObjectAtomic` 写入 `prepared`，紧接着 `restartClashOk({preparedConfig: prepared})`，而 `restartClash` :9270 又调 `writeYamlObjectAtomic(CLASH_CONFIG, preparedConfig)`——后者会**再跑一次** `kprShapeRuntimeConfig`，再写一次。

**代价**：多一次整形（`kprReadOptions` 一次 shell + `kprVerifySelection` 前的 mips 探针 + `dumpConfigYaml`）、一次 `Core -t`、一次原子替换。合计 2~3 次设备往返 + 一次核心校验进程。

**方案**：`preparedConfig` 已经是整形结果，重启时只做落盘：

```js
// restartClash :9270
if (preparedConfig) {
  const write = await kprBaseWriteYamlObjectAtomic(CLASH_CONFIG, preparedConfig, { label: 'config.yaml', backup: false });
  ...
}
```

**收益**：每次模式切换省一次完整整形 + 一次 Core -t。按 7895/TProxy 的往返实测口径，约 0.3~0.8 s。

**风险**：低。`prepared` 与二次整形结果应完全一致（整形是幂等的），去掉重复不影响结果。

---

### P2 mips 版本探针跑两遍

**现象**：JS 侧 `verifyF50TunStack`(:3064) 在每次 `kprShapeRuntimeConfig` 里探一次 `Clash.Core -v`；Service 侧 `f50_check_tun_stack`(:1643) 启动时用 `f50_check_mips_version`(:1630) 再探一次。同一次切换至少 2 次核心进程启动。

**方案**：JS 侧加短 TTL 结果缓存，键为 `traffic_mode|ipv6|tun_stack`，命中则跳过探针：

```js
let tunStackProbe = null; // { key, value, expires }
// verifyF50TunStack 内
const key = [options.traffic_mode, options.ipv6, options.tun_stack].join('|');
if (tunStackProbe && tunStackProbe.key === key && tunStackProbe.expires > Date.now()) return tunStackProbe.value;
```

**收益**：一次切换少一次 `Clash.Core -v`（ARM 上约 50~200 ms），订阅更新、自检修复等整形路径同样受益。

**风险**：低。TTL 取 60 s；换内核后最迟 60 s 纠正。若担心，可在 `invalidateBinarySnapshot` 里一并清空。

---

### P3 options.conf 被反复读

**现象**：`f50_check_tun_stack` 读 `traffic_mode`、`tun_stack`、`ipv6` 三次（:1643、:1644、:1650），`f50_prepare_tun_stack` 再读一次，`f50_finish_tun_stack` 与 `f50_tun6_return_route` 各自又读。一次启动 6~7 次 `grep`/`sed` 进程。

**方案**：抽一个读取函数，用一次 awk 把三个字段读进变量：

```sh
f50_load_tun_state() {
  f50_state_root=${CLASH_ROOT:-${F50_ROOT:-/data/clash}}
  f50_state_file="$f50_state_root/Policy/options.conf"
  [ -r "$f50_state_file" ] || return 0
  eval "$(awk -F= '/^(traffic_mode|ipv6|tun_stack)=/{printf "F50_ST_%s=%s\n",$1,$2}' "$f50_state_file")"
}
```

三个函数开头各调一次，后续用 `$F50_ST_traffic_mode` 等。

**收益**：6~7 个进程降到 3 个（每个函数 1 次），启动路径约省 30~80 ms。

**风险**：低。awk 解析的是简单 `k=v` 行，与现有 `sed -n 's/^k=//p'` 行为一致。

---

### P4 `f50_finish_tun_stack` 连续 5 次调用

**现象**：:1682 一行里串了 `policy apply` → `tun6_return_route apply` → `policy verify` → `tun6_return_route verify`。controller 的 `policy apply` 本身已经会重建并校验规则。

**方案**：先实测 `policy apply` 的退出码是否已包含验证；若包含，去掉 `policy verify` 与一次 `tun6_return_route verify`，只保留 apply + 回程路由。

**收益**：省 2 次 controller RPC。

**风险**：中。需要确认 controller 的 apply 语义，**未验证前不要动**。

---

## 二、可读性

### R1 `kprSaveNetworkState` 一个函数 130 行、六件事

**现象**：:3092-3190 混合了参数规范化、字段比对、策略快照、写设置、写配置、重启、回滚。读一次要滚动三屏。

**方案**：按职责拆成四个小函数，主函数只留编排：

```
normalizeNetworkState(next)           // :3099-3117
snapshotPolicyFiles(tag)              // :3125-3133
applyNetworkChange(next, prepared)    // :3137-3149
rollbackNetworkChange(tag, backup)    // :3167-3185
```

**收益**：主流程从 130 行降到 ~40 行，回滚逻辑可单独测。

**风险**：中。纯搬运，但涉及事务顺序，必须逐行对照。

---

### R2 `networkStateKey(state, runtimeOnly)` 命名反直觉

**现象**：`runtimeOnly = true` 时比较的键**更少**（不含 `quic_block`、`proxy_group` 和名单），实际语义是「只比运行时字段」。

**方案**：改名 `networkStateKey(state, { onlyRuntimeFields = false })`，调用点两处一起改（:3110、:3098 附近）。

**收益**：读代码时不用反推布尔含义。

**风险**：极低。

---

### R3 关键 shell 逻辑埋在模板字符串里

**现象**：`f50_check_mips_version`、`f50_check_tun_stack`、`f50_prepare_tun_stack` 都是几百字符的内联字符串，没有语法高亮、无法单独 grep 定位。

**方案**：`f50_check_mips_version` 已经是独立 builder，把 TUN 三个函数也抽成 `buildF50TunStackHelpers()`，与 `buildF50Ipv6DnsCompatFunctions()` 并列。

**收益**：可单独 `sh -n` 校验、可在测试里 slice 出来跑。

**风险**：低（纯搬移，注意 patch 里用的 marker 不变）。

---

### R4 魔法字符串两侧各写一遍

**现象**：`'traffic_mode=tun'`、`'ipv6=on'`、`'tun_stack='` 在 JS 判断（:3050、:3099）和 shell（:1643、:1644）里各出现一次。

**方案**：JS 侧定义 `const POLICY_KEYS = { mode: 'traffic_mode', ipv6: 'ipv6', stack: 'tun_stack' }`，shell 侧由同一 builder 用变量拼接。

**收益**：改字段名时只改一处。

**风险**：低。

---

### R5 `$tun6_root` 是隐式跨函数状态

**现象**：`tun6_root` 只在 `f50_check_tun_stack`(:1641) 赋值，`f50_prepare_tun_stack`(:1664) 直接用。函数间靠全局变量传参，读者无法从签名看出依赖。

**方案**：见 D1，各自初始化 + 显式传参。

---

## 三、可维护性

### M1 stack 决策逻辑存在三份

**现象**：`f50TunStack`(:9) 决定 `auto → mixed/gvisor`；`verifyF50TunStack`(:3064) 再叠一层 mips 版本门槛；`f50_check_tun_stack`(:1639) 在 Service 里把同样的规则再实现一遍。改门槛版本要动三处。

**方案**：JS 计算完后把最终值写进 options.conf（如 `tun_stack_resolved=mips`），Service 优先读它，读不到才自己探测。

**注意**：`parsePolicyOptionsText` 若对键做白名单过滤，新键会被丢掉，需先确认。

**收益**：版本门槛只维护一处；Service 少一次 `Clash.Core -v`（与 P2 叠加）。

**风险**：中。需要确认 policy 脚本不会因为多出的键报错。

---

### M2 受控键集合有两套

**现象**：`KPR.runtime` 里新增的 `CONTROLLED_TOP_KEYS` / `CONTROLLED_DNS_KEYS` / `CONTROLLED_TUN_KEYS`（:2832-2834），与 preserve 分支用的 `F50_ORIGINAL_MANAGED_KEYS` / `F50_ORIGINAL_DNS_KEYS` / `F50_ORIGINAL_TUN_KEYS`（:52-54）语义重叠但不一致。

**方案**：定义一张受控键表，两个分支从同一表派生（preserve 分支取其中「需要强制」的子集）。

**收益**：新增受控键时不会只改一边。

**风险**：中。改错会扩大或缩小放行范围，必须逐键对照。

---

### M3 `networkStateKey` 的键表是手写数组

**现象**：:3049 的数组与 :3053 的名单字段各自硬编码。新增一个影响配置的 options 字段（如上次讨论的 `quic_block`）时，很容易忘记加进去，表现为「改了设置但配置没重建」。

**方案**：把「影响 config.yaml 的 options 字段」显式声明为一个常量，并在保存时断言 `Object.keys(options)` 都在已知集合里，未知字段打 debug 日志。

**收益**：新增字段漏加时会暴露，而不是静默失效。

**风险**：低。

---

### M4 Service 侧三个 TUN 函数无自动化测试

**现象**：`run_tests.js` 只对生成的 shell 做 `sh -n`，`f50_check_tun_stack` 的分支（auto/mips/gvisor/mixed/非法值）没有被 fixture 覆盖。

**方案**：复用 `ipv6_dns.test.js` 的 fixture 方式（临时目录 + 假 core + 假 options.conf），断言四种 stack 选择与两种失败路径。

**收益**：改 Service patch 时能立刻发现回归。

**风险**：低。

---

## 四、潜在缺陷

### D1 `f50_prepare_tun_stack` 依赖未初始化的 `$tun6_root`

**问题**：:1664 直接用 `$tun6_root`，它只在 `f50_check_tun_stack`(:1641) 里赋值。若 patch 顺序调整、或 check 在子 shell 中执行，这里会拿到空值，`tun6_cfg` 变成 `/Proxy/config.yaml`，报 `tun_config_mismatch`——用户只看到「配置不匹配」，不会想到是路径问题。

**方案**：

```sh
f50_prepare_tun_stack() {
  tun6_root=${CLASH_ROOT:-${F50_ROOT:-/data/clash}}
  ...
}
```

**收益**：消除一类难以复现的启动失败。

**风险**：极低。

---

### D2 `mips_core_version_unavailable` 没有中文文案

**问题**：`f50_check_mips_version` 返回 2 时(:1631)，`f50_check_tun_stack` 原样输出并 `return 2`(:1652)，启动失败。但 `F50_DIAGNOSTIC_LABELS`(:1034) 没有这个键，用户看到的是裸错误码。

**方案**：补一条 `mips_core_version_unavailable: '无法读取 Mihomo 版本；请检查核心文件是否可执行'`。

**收益**：失败可诊断。

**风险**：极低。

---

### D3 `f50_finish_tun_stack` 失败不区分阶段

**问题**：:1682 用 `&&` 串联四步，任一步失败只 `return 1`，输出里看不出是 `policy apply` 失败还是回程路由失败，回滚也无从下手。

**方案**：逐步输出标记：

```sh
f50_run_controller policy apply || { echo F50_ERROR=tun_policy_apply_failed; return 1; }
f50_tun6_return_route apply || { echo F50_ERROR=tun_return_route_apply_failed; return 1; }
```

**收益**：`lastInstallDiagnostic` 能直接定位阶段。

**风险**：极低。

---

### D4 `restartClash` 的二次写入存在失败窗口

**问题**：:3138 写入成功 → :9269 再写一次，若第二次失败，配置已被第一次改掉，只能靠回滚点恢复。窗口短但存在。

**方案**：即 P1，去掉重复写入，窗口消失。

**收益**：少一个失败分支。

**风险**：无（与 P1 同一改动）。

---

### D5 `networkStateKey` 不含 `transparent`

**问题**：`kprSaveNetworkState`(:3103) 会改写 `next.options.transparent`，但它不在 :3049 的键表里。目前 UI 没有直接入口，属于隐性依赖；将来若开放「透明代理开关」，改了不会触发配置重建。

**方案**：把 `transparent` 加入键表，或从 :3103 改为派生值且不持久化。

**收益**：消除未来的静默失效。

**风险**：低。

---

### D6 `f50_tun6_return_route` 查询失败无错误码

**问题**：:1698 `ip -6 route show table 17667 exact "$prefix"` 失败直接 `|| return 1`，上层只看到「verify 失败」。

**方案**：补 `F50_ERROR=tun6_route_query_failed`。

**收益**：区分「路由不存在」和「查询命令失败」。

**风险**：极低。

---

### D7 `kprVerifySelection` 在切换中被调用两次

**问题**：:3120（重启前预检）与 :3148（重启后确认）各读一次 `/configs` 和 `/proxies`。预检是为了避免带着无效选择重启，属于有意设计；但两次都完整读 `/proxies`（可能很大）。

**方案**：保留预检，重启后只用 `/configs` 确认 mode 与选择未变，不必重读全部 proxies。

**收益**：省一次可能较大的 API 响应。

**风险**：低。需确认重启后选择确实不会变（理论上重启会恢复 `store-selected` 的持久选择，可能变，需实测）。

---

## 五、落地顺序

| 阶段 | 内容 | 理由 |
|---|---|---|
| 1 | P1/D4、D1、D2、D3、D6 | 低风险，纯收益，不改变任何判断逻辑 |
| 2 | P2、P3、R2、R3 | 需要改动 shell builder 与整形路径，有测试可依 |
| 3 | R1、M2、M3 | 结构性重构，需逐行对照 |
| 4 | P4、M1、D7 | 依赖实机确认 controller 语义与前端行为 |

## 六、验证方式

1. `node --check` + `verify_plugin.js` 全量（当前基线 627/0），阶段 1 不应减少用例数。
2. 为 `f50_check_tun_stack` / `f50_prepare_tun_stack` / `f50_finish_tun_stack` 补 fixture 测试（M4），覆盖 auto→mips / auto→gvisor / auto→mixed / 显式 mips 版本不足 / 非法值。
3. 性能项（P1~P4）用设备侧打点：在 `kprSaveNetworkState` 的每个 `operationStage` 前后记 `performance.now()`，对比改动前后同一操作的耗时。没有这组数据，本文的毫秒数只是估算。

## 七、不建议动的地方

- `f50_check_tun_stack` 里 `return "$mips_rc"`（把探针错误码原样上抛）：看似可以直接吞掉，但这会让「版本探针失败」被误当成「版本过低」而静默降级，掩盖真实故障。
- `auto` 的判定顺序（先 mixed/gvisor 再探 mips）：UI 文案「优先 mips，旧内核回退」依赖这个顺序，改成先探 mips 会多一次无谓的核心启动。
- `tun.stack` 受控：放行会让用户在旧内核上选 mips，core 直接起不来。
